# P0-05 example and answer contract decision

Status: **synthetic, unpublished design check**. [examples.synthetic.json](examples.synthetic.json) contains invented short strings and provisional answer variants for testing the contract. Its `synthetic-p0-05` source is local to the fixture, explicitly test-only, and absent from the deliberately empty [P0-04 source manifest](../../sources/manifest.json). No source rights, qualified Serbian review or answer correctness approval is implied. `validate_examples.py --publish` rejects the fixture. The assessment examples and keys are in a repository file for validator tests, so **they are not deployable unseen holdouts**.

## Minimal fields demonstrated

Each candidate carries a stable example ID and revision context (answer-policy ID/revision), source/item reference, outcome/role/family, leakage group, original Serbian script, NFC Serbian and Russian text, one primary target ID with code-point span and exact surface reconstruction, review status, and accepted answer variants. The eight synthetic records cover all four outcomes with a practice and an assessment family per outcome, both Serbian scripts, multi-token target spans, and alternative answers. They test structure, not linguistic adequacy. The final tasks may need different spans and answer policies after educator review.

The validator resolves families and target IDs against the P0-07 [pilot manifest](manifest.json). It checks source/item identity against P0-04 records or an explicit synthetic test-only source, rejects unresolved refs and missing translation, validates NFC code-point spans, and blocks split leakage by declared group, exact Serbian text after Serbian Cyrillic→Latin transliteration, and normalized Russian translation. This is a minimum deterministic screen. It cannot discover semantic paraphrases, changed names/numbers in the same template, or corpus ancestry; an editor must assign and review family IDs and near duplicates. For real items, publication preflight requires `redistribution` and `adaptation` permission decisions for **both text and translation**, plus approved item and answer-policy reviews. It must also protect actual answer keys from learner-visible materials.

## Existing storage inspected

- Legacy `VocabularyItem.example_sentences` and `example_translations` are nullable `Text` blobs. `domain_bootstrap_service._examples` preserves each entire blob as one `LegacyExamplePayload`; it does **not** split lines or prove bilingual alignment. Tests include a two-line bilingual blob and a translation-only blob. Do not promote or split old strings automatically, and do not treat them as reviewed pilot examples.
- `Sense.examples` and `Construction.examples` embed `UsageExample` values in JSON. `UsageExample` currently carries Serbian text, optional translation and a loose target annotation. This can hold a small reviewed source-linked example by adding versioned metadata in pack files, with the catalog's existing publication/revision lifecycle. `Form` already holds both written orthographies; there is no need for a separate example row to represent a script variant.
- `ActivitySpec.snapshot` accepts bounded portable JSON and pins the issued activity's target and content shape. A future practice adapter can snapshot the exact example/answer-policy revision and context/source family for replay, keeping private keys server-side before response submission. P0 adds no runtime adapter and no schema change.
- `catalog_mapping_service` fingerprints the original legacy example blobs along with other vocabulary fields and rejects stale mappings for evidence writes. That protects legacy/source identity but does not establish source rights, example-level approval or a safe one-to-one bilingual line pairing.

**Decision:** use a versioned file-backed pilot pack and existing embedded catalog examples for P1-03a/P1-04. Do **not** add an independent example table in P0 or trigger P1-03b yet. A concrete P1-03b trigger is demonstrated, approved reuse of the *same independently versioned example* across multiple senses/constructions or curricula **with separate retirement/withdrawal needs** that embedded parent revisions and issued snapshots cannot represent without duplicating identity or losing traceability. Before any such migration, inventory a sanitized representative legacy database for zero/unequal bilingual lines, edits, stale mappings and referenced activities, then document the failing file-backed/embedded case. The current synthetic fixtures demonstrate none of that.
